# 文書種別ごとの優先事項

固定テンプレートを当てはめるのではなく、読者が最初に必要とする情報と、残すべき材料を判断するために使う。

## 技術記事

優先するもの:

- 問題や問いを早めに示す
- 手順だけでなく採用理由と適用条件を残す
- 事実、観測、推測を区別する
- 実測していない効果を断定しない

## PR説明

優先するもの:

- なぜ変えたか
- 何が変わったか
- どこを見てほしいか
- どう検証したか
- 対象外や未確認範囲

実装ログを時系列に並べるより、レビュー判断に必要な情報を前へ置く。

## Issue

優先するもの:

- 現状
- 問題
- 期待する状態
- 対象範囲
- 完了条件
- 必要な制約

解決策を先に固定して、解くべき問題を見失わない。

## 設計メモ / ADR

優先するもの:

- 判断
- 背景と制約
- 選択肢
- 判断理由
- リスク
- 未決事項

一般的なベストプラクティスより、今回の判断条件を残す。

## 運用文書

優先するもの:

- 前提
- 手順
- 成功条件
- 失敗時の確認
- 中止条件やロールバック

理由説明と実行手順を混ぜすぎず、作業中に走査しやすくする。

## 業務連絡

優先するもの:

- 誰が対象か
- 何が変わるか
- いつからか
- 必要な行動
- 期限や例外

礼儀や背景説明で必要な行動を埋もれさせない。

## その他

既存の型へ無理に当てはめない。

読者が何を知りたいか、読後に何を判断・実行するか、何を保持しなければ意味が変わるかから構成を決める。
