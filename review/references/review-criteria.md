# Review Criteria

## 重要度レベル

各指摘の先頭に、次のラベルを一つだけ付ける。

- **Blocker**: 修正しないと、確認可能な条件で不具合、仕様逸脱、セキュリティ問題、データ破壊が起きる。マージ前に修正必須。
- **Major**: 動作は成立しても、根拠のある保守性、一貫性、運用上の問題が残り、放置コストが高い。マージ前の修正を強く推奨。
- **Minor**: 既存規約からの軽微な逸脱、可読性や明瞭さの改善。修正は任意だが推奨。
- **Nit**: タイポ、文言の揺れ、トリビアルなフォーマット違反。修正は任意。

Blocker と Major は、好みや未確認の推測には使わない。Nit はトリビアルな修正以外に適用しない。

## 探索後の品質ゲート

探索で作った候補ごとに、次を確認してから投稿可否を決める。

1. **仮説**: 差分によって起こると考えた問題を、一つの失敗経路として書ける。
2. **発生条件**: 入力、状態、権限、実行順序、環境、将来の変更など、問題が表面化する条件を具体化できる。
3. **根拠**: 差分、関連コード、テスト、仕様のどれが仮説を支えるか示せる。
4. **反証確認**: 呼び出し元、ガード、型、設定、公式仕様、テストを確認し、既に防がれていないと説明できる。
5. **差分との関係**: PR がその問題を導入または悪化させている。
6. **因果と影響**: 差分のどの処理や構造が、なぜ問題を起こし、利用者、データ、運用、後続処理、変更容易性の何へ影響するか説明できる。
7. **範囲**: 確認した事実を超えて、別ケースやコード全体へ一般化していない。
8. **判定と確度**: 下の判定と、影響に見合う重要度・確度を明示できる。

### 判定

- **成立**: 仮説、発生条件、根拠、反証確認、差分との関係、因果、影響を説明できる。重要度と確度が合えば投稿できる。
- **反証済み**: ガード、呼び出し元、型、仕様、テストなどにより失敗経路が閉じている。投稿しない。
- **判断不能**: 必要な仕様、実行時条件、一次資料、再現経路を確かめられない。投稿しない。

成立でも、重要度または確度を根拠とともに決められない候補は投稿しない。反証済み、判断不能な候補は投稿しない。

## 事実と不確実性

- コード、差分、テスト、仕様から確認した内容を事実として書く。
- 実行環境や仕様を仮定する場合は、その条件をコメント内へ明記する。
- 「可能性がある」だけでは指摘にしない。到達可能な失敗経路または具体的な変更コストを示す。
- 複数の原因や失敗経路を一つの問題としてまとめない。修正方法や影響が異なるならコメントを分ける。
- 「必ず防げる」「保証する」「解決する」は、成立条件を確認できる場合だけ使う。
- 例が主張の一部しか支えない場合は、主張をその例の範囲まで狭める。

## 投稿しないもの

- 差分の要約、一般的な称賛、説明だけのコメント。
- プロジェクト規約や実害に結び付かない好み。
- 到達条件を示せない仮想的な不具合。
- PR が触れていない既存問題。
- 同じ原因と失敗条件を言い換えただけの重複指摘。
