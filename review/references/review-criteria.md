# レビュー基準

## ラベル

各指摘の先頭には、次のラベルを一つだけ付ける。Blocker は影響の大きさだけでなく、マージ前に修正が必要かどうかで判定する。

- **Blocker**: マージ前に修正が必要な不具合、仕様違反、セキュリティ問題、データ破壊、主要機能の停止。
- **Nit**: タイポ、表記、機械的に直せる軽微な問題。
- **Consider**: 今回の差分が新たに作る具体的な変更容易性・保守性の問題についての検討提案。単に「よりきれい」「将来こちらの方がよい」「別設計なら拡張しやすい」という理由だけでは投稿しない。対応するか、別 Issue にするか、見送るかは担当者が判断する。
- **FYI**: 対応を求めない参考情報。

保守性・変更容易性だけを理由に Blocker にせず Consider とする。具体的な不具合や明示要件違反を伴う場合は、その失敗経路で判定する。

## 仕様と判断基準

レビュー開始時に整理した判断材料は、次の優先順位で正本として扱う。

1. Issue / PR に明示された受け入れ条件・禁止される結果。
2. リポジトリ内の仕様、公開契約、型、設定、テスト。
3. 既存コードから確認できる不変条件。互換性は明示要件または公開契約がある場合に確認する。

依頼文、Issue / PR 本文、既に読む規約・公開契約に後方互換・移行・段階導入・ロールバックの要求があるか確認する。自然言語の要求も含む。明示要件がなくても、公開 API・保存形式などの公開契約がある場合は、その契約と既存の利用側・データへの互換性を確認する。互換破壊や移行方針が明示されている場合も、上の優先順位に従う。要求・公開契約を超える旧実装・旧形式の維持は推測で要求せず、内部形式の変更だけを不具合としない。既存実装やテストがあるだけでは維持要件にならない。移行・段階導入・ロールバックは明示要件がある場合に確認する。不変条件、通常の例外処理、変更による部分失敗やデータ破壊の確認は省略しない。

今回の差分で不要になったコード・資料・テスト、要件にない互換処理、実装詳細を固定する過剰なテストは現在の要件に照らして確認する。全件チェックや単なる「もっと単純にできる」という指摘を増やさない。

AI がコードや PR の説明から推測した「こうあるべき」は、明示された要件や既存契約による裏付けなしに、単独では Blocker / Finding の根拠にしない。

明示的な仕様が不足していても、型・テスト・設定・公開契約などの既存契約から検証可能な範囲はレビューしてよい。不足部分を AI が新しい受け入れ条件として補完し、その推測との不一致を Finding にしてはならない。重要な判定を仕様不足で確定できない場合は、推測で Finding や問題なしの結論にせず、必要に応じて確認不能として報告する。確認のためにレビュー範囲を無制限に広げない。

compiler、type checker、test、linter、schema、既存 checker で合否を決定できる事項は、その結果を正本として使い、同じ合否を意味的レビューで再判定しない。レビューは、それらでは決められない意図、契約、失敗経路、要素間の整合性に集中する。ただし検査定義自体が今回の差分で変更されている場合は、その結果を無条件に正本とせず変更内容を確認する。

## Scope Gate

候補を深掘りする前に、次のすべてを確認する。一つでも満たさない候補は Rejected とし、それ以上 finding 化を試みない。

1. 今回の差分によって導入または悪化した問題の候補か。
2. PR / Issue の目的、完了条件、または維持すべき契約に関係するか。
3. **候補が真だと仮定した場合**、修正しなければ具体的な失敗、仕様違反、運用上の問題、または今回の差分が新たに作る変更容易性の悪化につながり得るか。

Scope Gate は候補のスコープと、真だった場合のアクショナビリティだけを判定する。ここで発生条件、失敗経路、因果関係の立証までは要求しない。それらは Concern を調査して Evidence へ昇格させる段階で確認する。

差分外の既存問題、好みだけの改善、将来のためのリファクタ、別アーキテクチャの方がよいという提案は Finding にしない。ただし今回の PR が導入・悪化させた問題や受け入れ条件・維持すべき明示契約の違反は、変更行の外で発覚しても今回の Finding として扱う。

偶然見つけた具体的な問題で、今回の PR が導入・悪化させず目的・受け入れ条件・維持すべき明示契約にも影響しないものは、深刻さにかかわらずレビュー本文の独立した「別 Issue 候補」節に根拠と無関係な理由を記し、切り出しを提案する。候補探しのために探索を広げず、起票もしない。Finding のラベル・件数や gate の blockers / important_unknowns に含めず、LGTM を止めない。根拠のない Concern、棄却した仮説、好みだけの改善は候補にも含めない。

## 候補の状態

レビュー内部の候補は、次の状態を区別する。これは GitHub 上へ追加ラベルとして出力するためのものではない。

- **Concern**: 怪しい可能性はあるが、発生条件、失敗経路、差分との因果関係、または根拠が未確立の候補。
- **Evidence**: 入力・状態・権限・順序・環境などの発生条件、失敗経路、影響、差分との因果関係を具体的に説明でき、第三者が確認できる再現または検証経路を持ち、差分・関連コード・テスト・一次資料のいずれかで裏付けられ、呼び出し元・ガード・型・設定・仕様・テストで反証されていない候補。
- **Rejected**: Scope Gate を通らない、反証された、根拠を確立できない、または品質ゲートを通らない候補。
- **Finding**: Evidence に昇格し、品質ゲートを通過して投稿可能になった候補。

検証経路は問題の性質に応じ、具体的な入力・状態・権限・実行順序、失敗する既存または追加可能なテストケース、呼び出し経路とガード条件を追えるコードパス、仕様 / 型 / 設定との決定的な不一致、再現可能なコマンドや操作手順のいずれかでよい。runtime reproduction や failing test は全 Finding に一律必須ではない。実行テストがなくても、決定的な不整合をコードと契約を追える静的な経路で検証できればよい。

Concern は探索の起点であり投稿対象ではない。「反証できなかった」「可能性を否定できない」こと自体を Evidence とみなしてはならない。具体的な根拠を確立できない Concern は Rejected とする。

ガード、呼び出し元、型、設定、仕様、テストなどで候補が反証された場合、その候補は Rejected として終了する。同じ原因と発生条件を言い換えただけの候補を再生成しない。再度扱うには、以前の反証を覆す新しい証拠が必要である。

Rejected は正常なレビュー結果であり、候補を棄却した埋め合わせとして別の finding を探す必要はない。

## 品質ゲート

Evidence の条件に加えて、次の 2 点を満たす候補だけを Finding として投稿する。

1. 一つの問題を扱っている。
2. 確認した範囲を超えて一般化せず、ラベルに見合う確度がある。

反証済みの候補や判断できない候補は Finding として投稿しない。差分と無関係な問題は Finding にせず、根拠がある場合だけ上記の独立節に分離する。好みだけの指摘、到達条件のない仮説、要約や称賛だけのコメントも Finding にしない。同じ原因と失敗条件を持つ候補は一つにまとめる。

品質ゲートを通過する Finding が 0 件でもレビューは成功である。十分な検証後の `0 findings` / LGTM を正常終了として扱い、指摘数を増やすために追加の仮説を生成しない。
