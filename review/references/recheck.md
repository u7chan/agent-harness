# Recheck Workflow

## 対象

- 明示的な再チェック依頼があった場合のみ実行する。初回レビューで投稿した直後の指摘は対象外とする。
- 以前の会話で投稿した未解決指摘だけを対象にする。
- 他者のコメント、別会話のコメント、再チェック中に新しく見つけた論点は含めない。
- 既に Resolve 済みの thread は対象外にする。
- 再チェック開始時に `pr.read` で最新の head commit SHA と Draft 状態を取得し固定する。途中で変更があればユーザーに報告する。

## ラウンド制限

- 同一 PR に対する再チェックは最大 3 ラウンドまで。
- 3 ラウンド後も Blocker が残存する場合、それ以上投稿せずユーザーに報告する。
- 最終ラウンドの投稿は常に COMMENT とする。

## 判定方法

元コメントから、指摘していた発生条件、原因、問題となる挙動、影響を再構成する。
変更行の有無ではなく、その失敗条件が現在のコードで到達可能かを確認する。

- **resolved**: 元の失敗条件が閉じ、同じ原因から問題となる挙動へ到達しない。
- **partial**: 一部の条件は閉じたが、元コメントに含まれる別の入力、状態、経路が残る。
- **unresolved**: 元の失敗条件がそのまま残る、または修正が別の場所に移しただけで影響が残る。
- **unknown**: 最新コード、実行時条件、仕様、権限の不足により根拠付きで判定できない。

テスト追加だけで resolved としない。実装が失敗条件を閉じていることを確認し、テストはその裏付けとして扱う。

## Draft PR の扱い

- Draft PR でも最大 3 ラウンドまで再チェックを継続する。
- 3 ラウンド後も Blocker が残存する場合は Draft のまま停止して報告する。
- PR が Draft でも Nit、Consider、FYI のみの残存であれば継続する。

## アクション

- **resolved**: 改善済みである根拠を短く返信し、ユーザーに Resolve の確認を取る。確認後に `review-threads.resolve` で Resolve する（sensitive-write のため自動実行不可）。
- **partial** / **unresolved**: 残っている発生条件と挙動を同じ thread へ返信する。
- **unknown**: 判断できない理由を報告し、Resolve しない。
- 返信できない場合だけ、必要に応じて overall comment で状態を伝える。
- 返信には重要度ラベルを更新して付ける（例: Blocker → Nit など、状況変化を反映）。
- 返信の `reply_to` には `review-comments.read` の出力に含まれる数値 ID を使う。`review-threads.read` の GraphQL ノード ID は `reply_to` に使えない。thread とコメントの対応付けは、以下の順で判定する：
  1. `review-threads.read` の `database_id`（REST 数値 ID）で直接 `reply_to` を特定する
  2. `database_id` が利用できない場合のみ、PR 番号とファイルパス、行番号、自アカウントのコメント、`in_reply_to_id` が `null` の root comment で照合する
  3. コメントが outdated の場合は `outdated` フラグを考慮し、original position を優先する
  4. 全条件で一意に特定できない場合は unknown として扱い、誤った thread への返信は行わない

## 直接修正

再チェック中に指摘内容を直接修正してよいのは以下の場合のみ：

- タイポの修正
- コメント（コードコメント）の修正
- Markdown ドキュメントの修正

以下の修正は不可：

- コードロジックの変更
- 設定値の変更
- テストコードの追加・変更
- 型定義の変更
- API シグネチャの変更

直接修正の可否は変更行数ではなく、修正の意味と影響範囲で判断する。判断に迷う場合は直接修正せず、指摘として投稿する。

## 最終報告

- 再コメント件数、Resolve 件数、ラウンド数を伝える。
- 未解決または判断不能があれば、その条件と理由を伝える。
- Blocker 残存による停止の場合は、残存指摘の一覧をレビュー記録テンプレート形式で報告する。
