# Posting Rules

## コメント本文

- PR 本文と同じ言語で書く。本文で判別できなければタイトル、それでも不明なら日本語を使う。
- 1コメントにつき、同じ原因と修正方針を持つ一つの論点だけを書く。
- 先頭に重要度ラベル（**Blocker** / **Nit** / **Consider** / **FYI**）を付ける。
- 成立条件、具体的な問題、原因、影響を、判断に必要な範囲で短く書く。
- 修正方針が一意または理解に必要な場合だけ、修正案を添える。
- Blocker 以外は Required ではないことが文面から分かるようにする。
- 「重要です」「懸念があります」など、論点を増やさない前置きや総括を書かない。
- 差分の要約、称賛だけのコメント、想像上の読者との問答を投稿しない。

指摘なしの review は重要度ラベルを付けず、確認した範囲で修正必須の指摘がなかったことを書く。
PR approval と誤解される表現は避ける。

## コメント位置

- 原因または修正対象に最も近い差分行へ inline comment を付ける。
- 直接付けられない場合は同じ hunk 内の最も近い差分行を使う。
- 複数ファイルにまたがる問題、削除済み行、API 制約で紐づけられない問題だけ overall comment にする。
- overall comment を総評や差分要約には使わない。

## レビュー記録テンプレート

レビュー実施後、以下の情報を必ず記録する。

| 項目 | 内容 |
|------|------|
| 対象 commit | レビュー時の head commit SHA |
| 実行検証 | 実行した取得・確認アクションの一覧 |
| 指摘一覧 | 重要度、ファイル、論点の要約 |
| 見送り理由 | 検討したが見送った候補とその理由（反証材料） |
| 残存指摘 | 前回レビューから未解決の指摘とその状態 |

## 指摘なしの review comment

指摘がない場合は、inline comment を作らず、review body のみを投稿する。
この場合も APPROVE は使わない。

## 投稿 API

すべての投稿操作は `gh/scripts/gh.sh` 経由で行う。API マッピングの詳細は `posting-api.md` を参照。

## 投稿後確認

- API 応答または再取得で、本文、ラベル、コメント位置を確認する。
- API 応答の decoded body（GitHub 上に表示される本文）を `rg` で検査し、リテラル `\n`（二文字として表示されるバックスラッシュ+n）、不完全な重要度ラベル、未置換の変数パターンをチェックする。JSON ペイロード内の `\n` エスケープは正常なため検査対象外とする。

## 禁止事項

- 投稿前のユーザー確認は不要。
- バッククォート、`$()`、引用符、改行を含む本文をシェル引数へ直接埋め込まない。
- JSON payload 内で実改行を使い、文字列としての `\n` を投稿しない。
- APPROVE review は発行しない。
- merge や issue close は行わない。
